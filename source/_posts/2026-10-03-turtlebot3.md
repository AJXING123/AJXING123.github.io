## 一、项目介绍

本项目的目标是在 Gazebo Classic 中搭建 TurtleBot3 Burger
仿真环境，并基于 ROS 2 Humble 完成一套完整的移动机器人导航流程：

-   在 Gazebo 中运行 TurtleBot3 Burger
-   使用 LiDAR 进行环境感知
-   使用 SLAM Toolbox 完成环境建图
-   保存二维栅格地图
-   使用 AMCL 在已知地图中进行定位
-   使用 Nav2 完成路径规划与运动控制
-   使用 Python Action Client 实现多目标点顺序导航
-   使用 Bash 脚本将 Gazebo、Nav2、AMCL 和多点导航程序串联起来

最终实现：

``` text
P1 → P2 → P3 → P4
```

机器人能够在 Gazebo 中依次前往四个预先记录的目标点。

> 2026-10 更新：本文最初以多点定点导航为目标，后续已加入运行时障碍物并实现动态避障绕行，完整过程见文末「十八、动态避障实战」。

## 四、建图流程

### 1. 启动 Gazebo

``` bash
export TURTLEBOT3_MODEL=burger
ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py
```

机器人提供：

``` text
/scan
/odom
/cmd_vel
```

以及 TF。

### 2. SLAM Toolbox 建图

``` bash
ros2 launch slam_toolbox online_async_launch.py use_sim_time:=true
```

数据流：

``` text
LiDAR
  ↓
/scan
  ↓
SLAM Toolbox
  ↓
/map
```

通过遥控机器人在 Gazebo 环境中运动，建立地图。

### 3. 保存地图

``` bash
mkdir -p ~/turtlebot3_ws/maps

ros2 run nav2_map_server map_saver_cli   -f ~/turtlebot3_ws/maps/turtlebot3_room
```

生成：

``` text
turtlebot3_room.pgm
turtlebot3_room.yaml
```

其中 `.pgm` 是地图图像，`.yaml` 保存地图元数据。

## 十二、项目中的重要知识

### 1. Topic

项目中使用：

``` text
/scan
/odom
/cmd_vel
/map
/initialpose
/amcl_pose
```

Topic 适合持续的数据流。

例如：

``` text
LiDAR → /scan
```

### 2. Service

Service 采用：

``` text
请求 → 响应
```

项目中用于生命周期、参数等操作。

### 3. Action

导航任务使用 Action：

``` text
NavigateToPose
```

因为导航是持续执行的任务，需要：

``` text
发送目标
 ↓
执行
 ↓
反馈
 ↓
结果
```

### 4. Lifecycle Node

Nav2 大量使用 Lifecycle Node：

``` text
unconfigured
inactive
active
finalized
```

理解生命周期，是理解 Nav2 启动和状态管理的重要基础。

### 5. use_sim_time

Gazebo 使用 `/clock` 提供仿真时间。

如果不同节点使用不同时间源，就可能产生 TF 时间错误，例如：

``` text
Lookup would require extrapolation into the future
```

因此仿真导航必须重视时间同步。

### 6. Gazebo 与 ROS 2

Gazebo 负责：

``` text
物理仿真
机器人模型
世界环境
传感器
```

ROS 2 负责：

``` text
节点
Topic
TF
导航
控制
```

两者通过 `gazebo_ros` 连接。

### 7. Nav2 插件系统

Nav2 的 Planner、Controller、Behavior 等功能通过插件加载。

本项目曾遇到插件名称不匹配问题，例如：

``` text
nav2_navfn_planner/NavfnPlanner
```

以及：

``` text
nav2_behaviors/Spin
nav2_behaviors/BackUp
nav2_behaviors/DriveOnHeading
nav2_behaviors/Wait
nav2_behaviors/AssistedTeleop
```

这说明 ROS 2 / Nav2
版本变化可能影响插件注册名称，排查插件问题时应以当前系统实际注册的
plugin description 为准。

## 十三、项目中的问题与排查

### Gazebo 无法生成机器人

排查了 Gazebo ROS Factory 插件以及：

``` text
libgazebo_ros_factory.so
/spawn_entity
```

最终确认 Gazebo ROS 插件正确加载后，可以正常生成 TurtleBot3。

### Nav2 Planner 加载失败

原因是插件名称不匹配：

``` text
nav2_navfn_planner::NavfnPlanner
```

修正为：

``` text
nav2_navfn_planner/NavfnPlanner
```

### Behavior Server 插件加载失败

同样修正插件名称格式：

``` text
nav2_behaviors/Spin
nav2_behaviors/BackUp
...
```

### AMCL 时间问题

曾出现：

``` text
Lookup would require extrapolation into the future
```

最终通过统一使用 Gazebo 仿真时间解决。

### ROS 2 DDS 网络发现问题

排查过程中发现本机存在 `FlClash` 网络接口，ROS 2
多播流量一度经过该接口，导致节点发现和服务通信出现异常。

这个问题说明：

> ROS 2 节点"看不到彼此"时，不一定是节点没有启动，也可能是 DDS Discovery
> 的网络路径出现问题。

### 自动启动时序问题

`start_nav.sh` 曾出现启动后等待 AMCL 的情况，但重新运行后又成功完成整个
P1→P2→P3→P4 导航。

因此目前将其视为：

> 启动阶段可能存在偶发的 ROS 2
> 节点发现/启动时序问题，后续可以继续优化启动脚本。

## 十八、动态避障实战（2026-10 更新）

项目最初版本只跑通了静态地图下的多点导航。本节记录后续加入运行时障碍物、实现动态避障的完整过程。

### 1. 障碍世界

使用自定义世界 `turtlebot3_world_obstacle.world`，在 P1 → P2 必经路线上放置一个障碍物：

``` text
obstacle_box
位置：(-1.92, 0.15)
尺寸：0.8m(x) × 0.3m(y) × 0.5m(z)
```

关键设计：**障碍物不存在于静态地图中**——SLAM 建图时没有它，运行时只能靠激光雷达实时感知，以此验证系统的动态避障能力。

机器人起点 (-2.0, -0.5)，P1(-2.07, -0.42) → P2(-1.77, 0.74) 的直线连线恰好穿过箱子，机器人必须绕行（从箱子右侧 x > -1.52 通过）。

### 2. 问题现象

加入障碍物后出现三类典型症状：

-   机器人在障碍前**徘徊振荡**，无法决策
-   RViz 中全局路径已经绕行，但机器人**不跟随**
-   频繁触发恢复行为（清图、自旋、后退），陷入循环

### 3. 排查与根因

逐项排查后定位到几个问题：

  问题                                       影响
  ------------------------------------------ ------------------------------------------
  障碍代价权重过低                           轨迹评分中"贴障"惩罚被"跟路径"奖励淹没
  膨胀半径过大（0.5m）                       可通行通道被膨胀区彻底堵死
  允许倒退（min_vel_x < 0）                  引入前后摇摆振荡
  obstacle_layer 与 voxel_layer 共用同一 /scan   同一束激光被重复标记，清除状态不一致

> 教训：避障异常时，不要只盯控制器参数，先检查 costmap 各层是否重复标记、膨胀区是否堵死了通道。

### 4. 最终方案

经过多轮迭代，最终稳定配置（`config/burger_nav2.yaml`）如下。

**Costmap 分层膨胀**

  参数                  全局     局部     理由
  --------------------- -------- -------- ------------------------------------------------------------
  inflation_radius      0.30     0.15     全局让规划路径离箱 ≥0.30m；局部 0.15 = 机器人半径 0.1 + 0.05 余量，避免机器人自己被膨胀区困住
  cost_scaling_factor   5.0      5.0      代价梯度更陡，靠近障碍时代价快速上升
  plugins               static + obstacle + inflation   obstacle + inflation   移除 voxel_layer，消除同一 scan 的重复标记

**控制器：RegulatedPurePursuit**

由 DWB 切换为 Regulated Pure Pursuit，关键参数：

  参数                       值          说明
  -------------------------- ---------- --------------------------
  desired_linear_velocity    0.25       巡航速度（m/s）
  max_angular_velocity       1.0        保证足够的转向能力绕障
  allow_reversing            false      禁止倒退，消除前后摇摆
  max/min_lookahead_dist     0.6 / 0.3  前瞻距离适配 5m 级房间尺度

**规划与恢复**

-   NavFn `tolerance: 0.5`：终点附近若存在运行时障碍标记（激光噪声、AMCL 漂移），允许在 0.5m 半径内搜索替代自由终点，避免 create_plan 直接失败
-   progress_checker：15 秒内必须移动至少 0.3m，只有真实停滞才触发恢复
-   `multi_point_nav.py` 增加失败自动重试：**重试前先清空 costmap**，清除陈旧障碍标记后再重新发送目标点

### 5. 验证结果

  点位               结果   说明
  ------------------ ------ ------------------------------------------------------
  P1 (-2.07, -0.42)  ✅     正常到达
  P2 (-1.77, 0.74)   ✅     成功识别箱子并从右侧绕行通过
  P3 (0.55, 0.43)    ❌     NavFn 规划失败：终点紧贴墙壁膨胀区，需调整点位或放宽 goal 容差

避障核心目标——识别运行时障碍并绕行——已在 P1 → P2 路段验证通过；P3 失败属于点位选址问题，与避障能力本身无关，留待后续修正。

### 6. 经验总结

``` text
避障排查顺序建议：
costmap 层配置 → 膨胀参数 → 控制器类型/参数 → 恢复行为链
```

1.  先确认障碍是否被正确标记（RViz 查看 costmap，或 `ros2 topic echo` 对应话题）
2.  膨胀半径不是越大越安全——过大会堵死通道、困住机器人
3.  差速小车在狭窄房间场景，Pure Pursuit 类控制器往往比 DWB 更容易调稳定
4.  允许倒退（负 min_vel_x）是振荡的常见根源
